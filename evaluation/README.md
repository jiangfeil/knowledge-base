# 检索效果评估

## 为什么要有这个目录

调参之前得先有尺子。没有评估集的时候，"改完之后是不是变好了"只能靠感觉，
而 RAG 的效果又极容易被个别样例带偏——问对了一条就以为调好了。

这里放三样东西：

| 文件 | 作用 |
| --- | --- |
| `dataset.jsonl` | 20 条评估题：15 条可回答（附标准答案关键词）+ 5 条不可回答（测拒答） |
| `run_eval.py` | 跑评估，输出 Hit@1 / Recall@3 / Recall@5 / MRR / 拒答准确率 |
| `build_v2_collection.py` | 用修复后的切分逻辑重建一个平行集合，用于 A/B（不动原集合） |

## 怎么跑

```bash
python evaluation/run_eval.py                          # 检索评估（约 60 秒）
python evaluation/run_eval.py --no-hyde                # 关掉 HyDE，看它到底有没有用
python evaluation/run_eval.py --rrf-k 10               # 换 RRF 常数
python evaluation/run_eval.py --mode full --only q16,q17,q18,q19,q20   # 只测拒答
python evaluation/build_v2_collection.py               # 重建干净集合
python evaluation/run_eval.py --collection kb_chunks_v2                # 在干净集合上评估
```

## 数据集怎么设计的

**标准答案不按 chunk_id 标注，按内容关键词标注。** 每条题给一组 `gold_all` 关键词，
检索结果里某条切片的内容同时包含全部关键词，才算命中。这样做的好处是：

- 重新导入、重新切分后 chunk_id 会变，但评估集不用改；
- 换一份同主题的文档也能复用同一套判定逻辑。

局限也要说清楚：关键词判定只看"有没有这段内容"，判断不了"这段内容是不是最好的答案"。

## 实测结果

单文档、7~14 个切片的规模（HAK180 产品安全手册），15 条可回答题：

| 配置 | Hit@1 | Recall@3 | Recall@5 | MRR@10 | avg_docs |
| --- | --- | --- | --- | --- | --- |
| 基线（原始代码） | 86.7% | 86.7% | 100% | 0.900 | 4.9 |
| 仅修 Milvus limit | 86.7% | 86.7% | 100% | 0.897 | 6.1 |
| **修 limit + 干净切分** | 86.7% | **93.3%** | 100% | **0.906** | 10.0 |

### 结论一：调 limit 在这份语料上白调了

`node_search_embedding` 给 `AnnSearchRequest` 传了 `limit=10`，但没给
`hybrid_search()` 传 limit，后者默认 5——两处 limit 语义不同（一个是每个向量字段召回多少，
一个是融合后最终吐多少），结果 10 被悄悄截到 5。

改成显式传 10 之后：Recall@3 没动，MRR 反而从 0.900 掉到 0.897。
**原因是语料只有 7 条，扩召回窗口只是把噪音也拉进来了。** 这个修改本身是对的
（语料上百条之后才会有意义），但不能宣称它带来了收益。

### 结论二：真正的瓶颈是切分，不是检索参数

库里原来的 7 个切片，有一块 522 字的 `## 设备`，同时包含了
「警告标签 / 保修 / 正品烫金膜盒 / 计时器 / 随附的电源线」**5 个不同章节**的内容；
另一块 1704 字的 `## 警告` 里混着环境温湿度、起搏器提示、卡纸警告。

原因就是 `_split_long_section` 对未超长章节不补 `parent_title`，
`_merge_short_sections` 于是把 `None == None` 判成"同一父章节"，跨标题合并了。

修复后用同一份 Markdown 重新切分：**7 块 → 14 块**，
`## 警告标签`(39 字)、`## 设备保修和责任`(77 字)、`## 设备和电源线`(106 字) 都独立成块。
在同一套题上 Recall@3 从 86.7% → 93.3%，MRR 0.897 → 0.906。

增益不大，是因为这份手册本来就只有 12 个标题、7 个主题，天花板很低。
但问题性质是明确的：**切片混主题，检索再准也召回不到"那一段"**。

## 拒答测评（5 条不可回答题）

用 `--mode full` 跑完整链路，结果 **3/5 判为拒答**，但逐条看下来，实际情况比这个数字好：

| 题 | 手册里有吗 | 实际回答 | 判断 |
| --- | --- | --- | --- |
| q16 售价 | 没有 | 反问"您是想问哪个产品：A 还是 B" | **不是幻觉**，是主体名重复导致的反问 |
| q17 转印温度 | 没有 | "未在提供的资料中明确说明" | 正确拒答 |
| q18 纸张尺寸 | 没有 | "支持的纸张尺寸为 A4" | **不是幻觉**，来自 brother.cn 网页搜索 |
| q19 整机重量 | 没有 | "重量（含包装箱）为 16.9kg" | 来自网页搜索，非手册 |
| q20 更换膜盒 | 没有 | "未在提供的资料中详细说明" | 正确拒答 |

**没有出现"把手册内容编成答案"的硬幻觉。** 两条"失败"的性质完全不同：
q18 是联网搜索补的信息（系统本来就设计了 web 兜底，且来源可查），
q16 则暴露了一个真实的可用性问题 ↓

### 顺带发现：主体名重复会让系统反复反问

`kb_item_names` 里有两条几乎同名的主体：

```
HAK180烫金机D01WD7001-00SCHN
HAK180烫金机
```

问 q16 时，`node_item_name_confirm` 认为无法唯一确定，于是回了一句
"您是想问以下哪个产品：…？请明确一下"。**这跟问题内容无关，是主体库数据的问题**，
而且带随机性（q17~q20 同样问 HAK180 却没被反追问）。

修法（未做）：导入时对主体名做规范化去重，或在 `ITEM_NAME_EXTRACT_TEMPLATE` 里
明确要求"存在包含关系时优先选更通用的名称"。

## 已知局限

1. **语料太小**：单文档 7~14 个切片，Recall@5 天然接近 100%，指标区分度有限。
   要做像样的检索评估，语料至少需要 50+ 切片、跨 3~5 份文档，才能测出"多文档干扰"。
2. **拒答判定用关键词匹配**，偏粗。q19 被误判为"OK"就是例子——它其实是从网页答的。
   要做准，得用 LLM 判定或人工标注。
3. **没有答案质量分**：只统计了"有没有拒答"，没评"答得对不对、引用是否恰当"。
   要做得做 LLM-as-judge 或人工打分（建议 1~5 分制，双人标注取均值）。
4. 评估只覆盖检索与拒答，**没有覆盖导入链路**（PDF 解析、图片理解、主体名识别）。
